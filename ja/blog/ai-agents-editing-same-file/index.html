2 つの AI エージェントが同じファイルを編集するとき — 互いに上書きさせない方法

2026年10月19日 · DobbyLab · claude-codecodexgit-worktreemerge-conflictsparallel-agents

2 つの AI エージェントに互いの変更を上書きさせないには、それぞれに git worktree を用意してマージ前に重なりを見つけるか、同じフォルダを共有するなら、編集する前に相手が何をしているかを互いに知らせることです。何が起きるかは、どこで作業しているかで変わります。別々の git worktree なら上書きは起きませんが、あとでマージ時にコンフリクトします。対策は、重なりを早めに見つけることです。同じフォルダでは、一方のエージェントがもう一方の作業途中の変更をそのまま書き換えてしまうおそれがあるので、編集する前に相手が何をしているかを知る必要があります。どちらも git で手動確認できますが、gtree は常時チェックし、同じフォルダの場合はさらに一歩進んで、エージェント同士に互いの存在を知らせ、伝言で「どちらが先に変更するか」を決められるようにします。

2 つのエージェントが同じファイルに触れると、実際に何が起きる?#

状況は 2 種類あり、それぞれ対処が異なります。

別々の worktree。 各エージェントは専用の作業フォルダとブランチを持つので、互いの編集は見えません。両方が src/auth.ts を変更し、どちらもテストに通り、2 本目のブランチをマージしたときに初めてコンフリクトが出ます。同じ関数をそれぞれ作り直していれば手作業で解決するしかなく、しかも双方がなぜそう変えたのか、もう覚えていないことがほとんどです。

同じフォルダ。 2 つのセッションが、隔離のない 1 つの作業ディレクトリを共有します。いちばん単純な事故は Claude Code 自身が防いでいます。最後に読んだ後でファイルが変わっていれば編集を拒否するので、古い内容を黙って書き戻すことはありません。本当のリスクはもっと見えにくいところにあります。エージェント B がファイルを読み直してエージェント A の新しい変更を目にし、それが A の作業途中のものだと知らないまま上から書き換えてしまう。あるいは A の作りかけの変更で B のビルドが壊れる(逆もあります)。

並列で動く AI エージェントの衝突を防ぐには?#

どんなツールを使う場合でも、次の習慣が役立ちます。

  1. 手順ではなく領域で分担する。 「検索 UI」と「ログインのレート制限」はめったに衝突しません。「auth のリファクタリング」と「OAuth の追加」はほぼ確実に衝突します。
  2. 担当を明示する。 各エージェントのプロンプトで、担当するファイルやディレクトリと、触ってはいけない場所を伝えます。
  3. エージェントごとに worktree を分ける。 気づかない上書きが、目に見えるマージコンフリクトに変わります。後者のほうがずっと扱いやすいです。
  4. 小さく、こまめにマージする。 1 時間で終わるブランチはまず衝突しませんが、1 週間続いたブランチはたいてい衝突します。

git で変更の重なりを確認する方法#

worktree をまたいだ未コミットの変更。 次のスクリプトは、2 つ以上の worktree で未コミットの変更があるファイルを一覧表示します(パスに空白を含まない前提の簡易版です)。

git worktree list --porcelain | awk '/^worktree /{print $2}' |
while read -r wt; do
  git -C "$wt" status --porcelain | awk -v wt="$wt" '{print $NF, wt}'
done | sort | awk '
  { n[$1]++; w[$1] = w[$1] " " $2 }
  END { for (f in n) if (n[f] > 1) print f ":" w[f] }'

2 本のブランチでコミット済みの変更。 それぞれが main から分岐した後に変更したファイルを出して比べます。

git diff --name-only main...fix-login
git diff --name-only main...search-box

本当にコンフリクトする? Git 2.38 以降なら、merge-tree で作業フォルダに触れずにメモリ上でマージを試せます。

git merge-tree --write-tree fix-login search-box

きれいにマージできれば終了コードは 0、コンフリクトがあれば 1 を返し、該当ファイルを表示します。

どのコマンドも有効ですが、実行し忘れれば意味がありません。そして未コミットの重なりこそ、エージェントの作業中に刻々と変わるものです。同じフォルダにいる 2 つのエージェントについては、これらのコマンドは何の助けにもなりません。

同じフォルダの 2 つのエージェントは、どうやって順番を決める?#

git からはまったく見えないケースで、gtree がもっとも細かく扱う部分です。Claude Code か Codex を接続すると、gtree はどのセッションがどのファイルを編集したかを記録します。同じフォルダの 2 つのエージェントが同じファイルを編集しようとすると、次のように進みます。

  1. エージェント A が src/auth.ts を編集する。 gtree はその編集を A のセッションに記録します。エージェントのファイル編集ツールだけでなく、sed や Python スクリプトなどのシェルコマンドによる変更も見分けます。
  2. エージェント B が同じファイルを編集しようとする。 編集が反映される前に、gtree は B のコンテキストにメモを加えます。src/auth.ts は数分前に、まだ開いている別のセッションが変更したこと(gtree は 30 分前までさかのぼります)、そのセッションが何に取り組んでいるか、このフォルダは git で隔離されていないので先にファイルを読み直すこと。同じ箇所を変更する必要があるなら、gtree の tell ツールで相手と「どちらが先に変更し、どちらが待つか」を決めること。
  3. A にも伝わる。 作業中のファイルを別のセッションに変更された側にもメモが届きます。あなたが作業中のファイルを別のセッションが変更した、自分が書いていない部分は相手のものなので、事故だと思って元に戻さないように、という内容です。
  4. 話し合う。 B は tell で A に伝言を残します(「login() もこちらで変更が必要です。そちらは終わりましたか?」)。A は次にファイルを編集したとき、シェルコマンドを実行し終えたとき、またはあなたが次に話しかけたときにそれを読みます。未読の伝言を残したままターンを終えようとすると、先に読むよう引き止められます。A も同じ方法で返事をします。
  5. 先に変更した側は、終わったら知らせる。 ターンが終わると、gtree は伝言をやり取りしていたセッションに「このターンは終わった、変更したのはこのファイル」と自動で伝えます。待っていた側は次のステップか、あなたが次に話しかけたときにそれを読み、作業を続けられます。
  6. ビルドが壊れても、原因を取り違えない。 B のビルドやテストが、別の稼働中のセッションが直前に変更したファイルで失敗した場合、B には「おそらく自分のバグではない。相手のファイルには手を出さず、tell で知らせ、その間はビルドが通らなくてもできる作業を進める」というメモが届きます。

これらはすべてエージェントの会話の中で起こります。gtree がダイアログを出したり、あなたに判定を求めたりすることはなく、編集をブロックすることもありません。エージェントが読んで自分で従うメモです。Claude Code と Codex の間でも同じように動くので、同じ worktree にいる Codex のセッションと Claude Code のセッションも、同じように声をかけ合います。

やり取りの様子は**「対応待ち」**(⌘1)で追えます。あるエージェントが別のエージェントに残した伝言は、受け取る側が作業中かあなた待ちのときはその行の下に表示され、まだ読んでいなければ「未配達」と表示されます。受け取る側が待機中で、伝言が 10 分以上届いていない場合は、「念のため確認」に 1 行として表示されます。

2 つの worktree が同じファイルを変更しているとどうわかる?#

別々の worktree どうしは互いを上書きできないので、ここでの目標はマージ前に気づくことです。gtree はすべての worktree のファイルを監視し、ディスク上の変化から約 1.5 秒で更新します。2 つの worktree が同じファイルを変更していると、次の 3 か所で確認できます。

  • サイドバー。 その行にセッションの状態アイコンが出ていなければ(開いているセッションの状態アイコンがあればそちらが優先)、行末に琥珀色の △ が付きます。ホバーすると、他でも変更中のファイル数が出ます。
  • スタートページ。 その worktree をクリックすると「N 件のファイルが別の場所でも変更されています」と表示され、**「どれか見る」**でファイルと関係する worktree を一覧できます。
  • 「対応待ち」。 どちらもまだコミットしていない重なりは**「念のため確認」**に、関係する worktree の組み合わせごとにまとめて表示されます。

gtree が示すのは、少なくとも一方がまだ未コミットの重なりだけです。2 つのエージェントが実際に同じファイルを変更しているのはそういうときだからです。両方がコミット済みなら、マージ時に git が教えてくれますし、上の git merge-tree で本当のコンフリクトかどうかもわかります。

種類 意味 どこに表示されるか
どちらも未コミット 2 つのエージェントがいままさに変更している サイドバーの △、スタートページ、「対応待ち」
片方はコミット済み、片方は未コミット 一方は終わり、もう一方はまだ変更中 サイドバーの △、スタートページ

「対応待ち」の各項目には**「比較を見る」ボタンがあり、何が変わったかを開けます。閉じるには、ホバーして「了解」**をクリックするか ⌫ を押します。同じ worktree の組み合わせで重なるファイルが増えたり、状況が変わったりすると、また表示されます。AI ツールがサブタスク用に作る一時的な worktree は対象外なので、ノイズになりません。

誰がファイルを編集中か、エージェント自身が確かめられる?#

Claude Code か Codex を接続すると、各セッションで gtree のツールが使えるようになり、エージェントは知らされるのを待たずに自分で確かめられます。

  • who_touches は「このファイルをほかに誰が変更しているか」に、同じリポジトリの各 worktree と、このプロジェクトに依存する下流のプロジェクトを対象に答えます。現在のフォルダについては、セッションごとに分けて答えます。
  • who_is_working は、ほかのエージェントがいま何をしているかを一覧します。
  • tell は、上で紹介したとおり、別のセッションに伝言を残します。

新しいセッションは、最初に短いブリーフィングも受け取ります。同じフォルダや関連プロジェクトで誰が作業中か、そして新しく作らずに再利用できる既存の worktree(マージ済みで、未コミットの変更がなく、どのセッションも使っていないもの)です。これで、何かを書く前に混み合っている場所を避けられます。

gtree はファイルをロックしたり、編集を止めたりする?#

これはメモと目印であって、ロックではありません。gtree は重なりをあなたとエージェントに知らせますが、編集を止めたりエージェントを一時停止したりはしません。待つかどうかは、メモを読んだエージェントが判断します。また検出はファイル単位なので、同じファイルの別々の関数を変更していてもメモが届きます。たいていは読み直して、そのまま作業を続けます。

よくある質問#

2 つの Claude Code セッションを同じフォルダで動かせますか?#

動かせますが、すべてのファイルを隔離なしで共有するので、いつ編集がぶつかってもおかしくありません。本格的に並列で作業するなら、セッションごとに git worktree を用意しましょう。どうしてもフォルダを共有する場合、gtree は一方が直前に変更したファイルをもう一方が編集する前に知らせ、伝言でどちらが先かを決められるようにします。

Claude Code はファイルが変更されたことに気づきますか?#

一部は気づきます。最後に読んだ後でファイルが変わっていれば編集を拒否し、読み直しを求めます。ただし、誰がなぜ変えたのかはわかりません。その文脈を補うのが gtree です。

Codex でも使えますか?#

使えます。Codex のセッションも、別のセッションが直前に変更したファイルを編集する前に同じメモを受け取り、tell を使え、同じ「終わった」の知らせを送ります。同じフォルダにいる Claude Code と Codex のセッションも、Claude Code 同士と同じように声をかけ合います。

同じファイルを変更したら必ずコンフリクトしますか?#

いいえ。同じファイルでも別の箇所の変更なら git が自動でマージします。重なりは「マージ前に確認を」という合図で、本当にコンフリクトするかは git merge-tree でわかります。

自分のターミナルで起動したエージェントでも使えますか?#

使えます。worktree をまたぐ重なりの目印は git から得るので、ほかに何もいりません。同じフォルダでのメモは Claude Code と Codex の hook から来ており、接続すればどのターミナルのセッションからも報告されます。

gtree のローカル機能は無料で、登録も不要です。gtree があなたのコードをアップロードすることはありません。gtree をダウンロードして、どの worktree がすでに重なっているか確かめてみてください。どのセッションがあなたを待っているかを知るには、Claude Code の承認待ちに気づく方法をどうぞ。
