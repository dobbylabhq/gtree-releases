# gtree が Electron を使わない理由 — 24 MB、0.2 秒でウィンドウ表示

> gtree は Rust で書かれ、画面は Zed エディタの GPU 描画フレームワーク GPUI で描いています。ブラウザも Node も同梱していません。ネイティブで何が得られるのか、実測値と測り方をまとめました。

Published: 2026-10-25 · DobbyLab · https://gtree.dobbylab.com/ja/blog/gtree-native-app-not-electron/

gtree はネイティブのデスクトップアプリで、Electron でも Web ビューでもありません。Rust で書かれ、画面は **GPUI**(Zed エディタの UI フレームワーク)が GPU で描画し、パッケージにはブラウザエンジンも Node ランタイムも入っていません。ダウンロードは **24 MB**。Apple M4 での実測では、ウィンドウ表示まで**約 0.2 秒**(ウォームスタート)、アイドル時のメモリは**約 100 MB** です。本記事では、複数の AI コーディングエージェントを動かすときになぜこれが効くのか、中身はどうなっているのか、そして数字をどう測ったのかを説明します。

## AI エージェントを見守るツールは、なぜ軽くあるべきなのか?

3〜4 つのエージェントが[それぞれ専用の git worktree で](/ja/blog/run-multiple-claude-code-git-worktree/)作業していると、Mac はすでに忙しい状態です。どのエージェントもビルドやテスト、開発サーバーを動かし、worktree ごとに `node_modules` や `target/` があります。それらを見守るアプリは、できるだけリソースを使わないほうがいいはずです。

gtree がネイティブなのは、この一点のためです。Electron 製のデスクトップアプリは Chromium と Node.js を丸ごと同梱し、ウィンドウはそれぞれ Web ページです。多くのアプリにとっては妥当なトレードオフですが、一日中開きっぱなしでコンパイラやエージェントと同じマシンを使うツールなら、メモリとディスクはあなたの作業に回したいと考えました。

## gtree は何で作られているのか

- **Rust**。ネイティブの arm64 実行ファイル 1 つにコンパイルされます。
- 画面は **GPUI**。Zed エディタと同じフレームワークで、GPU 上で **Metal** を使って描画します。Web ビューはありません。Electron でも Tauri でも WKWebView でもなく、アプリの Resources フォルダにあるのはアイコンファイル 1 つだけです。
- 読み取りの大半(履歴、ブランチなど)には純 Rust 実装の **gitoxide**。一部の状態や差分のチェックは git を直接呼び出します。
- 書き込み(コミット、プッシュ、プル、リベース)は**お使いの `git`** を呼び出します。SSH キー、認証情報、git hook はターミナルで使うときとまったく同じように効きます。
- **内蔵ターミナル**は自前の `gpui-term`。端末プロトコルの解析は `alacritty_terminal`、描画は GPUI です。中で動くのは本物のエージェント CLI(Claude Code または Codex)で、再実装ではありません。
- **検索**は `git grep -F`。⌘P のファイル検索は、すでにメモリにあるファイルツリーを引くので、ディスクを読み直しません。

## どれくらい速いのか:実測値

| 項目 | 実測値 | 測り方 |
|---|---|---|
| ダウンロード(zip) | **23.6 MB** | GitHub Release 上の `gtree-0.3.14-macos-aarch64.zip` のサイズ |
| インストール後のアプリ | **73 MB** | インストール済み `.app` に `du -sh`。ほぼすべてが 1 つの実行ファイルで、Resources は 1.1 MB のアイコンのみ |
| 起動からウィンドウ表示まで | **162〜206 ms**、中央値 176 ms(7 回) | プロセスを起動してから、そのアプリの最初のウィンドウが画面に出るまでを 2 ms ごとに確認。**ウォームキャッシュ**で、再起動直後のコールドスタートではありません |
| 起動からリポジトリ読み込み完了まで | **458〜574 ms**(3 回) | プロセス起動から、6 つの worktree・14 ブランチ・200 コミットの読み込み完了がログに出るまで |
| アイドル時のメモリ | **93〜99 MB** | アクティビティモニタの「メモリ」(物理フットプリント)。起動 30 秒後から 2 秒ごとに 20 秒間計測 |

**計測環境**:Apple M4(10 コア)、メモリ 24 GB、macOS 15.3.1、gtree 0.3.14 正式版。リポジトリは gtree 自身のリポジトリのローカルクローン(366 コミット、474 ファイル)に worktree を 5 つ追加したもので、それぞれに 1 コミットと 1 つの未コミット変更があり、サイドバーには 1 プロジェクト・6 つの worktree が並ぶ状態です。一時的なホームフォルダを使い、利用統計はオフにして、実際のプロジェクトや設定には触れていません。

これは 1 台のマシンでの計測で、ベンチマークスイートではありません。リポジトリの大きさや開いているプロジェクトの数によって数字は変わります。

## 大きなリポジトリでも重くなりませんか?

ネイティブであることは一部にすぎません。残りはコードベースのいくつかのルールが支えています。

- **長いリストは見えている行だけを描く。** コミット、ブランチ、差分の行、ファイル、過去の会話はすべて仮想スクロールなので、数千行のリストでも描くのは画面に見えている数十行だけです。
- **重い git 処理はバックグラウンドで。** 履歴の読み込み、差分の計算、どのブランチがマージ済みかの判定はメインスレッドの外で行うので、その間もウィンドウは操作できます。

## gtree はコードをアップロードしますか?

しません。gtree がコードをアップロードすることはありません。ローカル機能は無料で、アカウントも不要です。エージェントは gtree がないときと同じように各自のサービスとやり取りし、gtree はお使いの Mac 上の hook を通じてその状態を読むだけです。

権限については、gtree が求めるのは通知だけで、それも任意です。フルディスクアクセス、アクセシビリティ、画面収録は必要ありません。アップデートはリリースページからダウンロードし、SHA-256 チェックサムを照合してからアプリを置き換えます。

## 制限事項

- 現在は **Apple Silicon の macOS のみ**対応です。インストーラは arm64 です。
- 現時点では**オープンソースではありません**。
- **この記事は起動時と静止時についてです。** 「複数のエージェントが同時に動いているとき」の数字は、続報で公開します。

## よくある質問

### gtree は Electron や Tauri で作られていますか?

どちらでもありません。Rust のネイティブアプリで、画面は GPUI が GPU(Metal)で描画します。中に Web ビューはありません。

### gtree のサイズは?

ダウンロードは 23.6 MB、インストール後は 73 MB で、そのほとんどが 1 つのネイティブ実行ファイルです。

### 起動はどれくらい速いですか?

Apple M4・ウォームキャッシュの条件で、ウィンドウ表示まで 162〜206 ms(中央値 176 ms)、6 つの worktree があるリポジトリの読み込み完了まで約 0.5 秒でした。

### メモリはどれくらい使いますか?

計測環境では、1 プロジェクト・6 つの worktree を開いた状態で、アイドル時に約 93〜99 MB(アクティビティモニタの値)でした。

### どのエージェントに対応していますか?

Claude Code と Codex です。最初に対応し、連携がもっとも深いのは Claude Code です。

### Intel Mac、Windows、Linux で使えますか?

まだ使えません。現在のリリースは Apple Silicon の macOS 向けです。

gtree のローカル機能は無料で、登録も不要です。gtree があなたのコードをアップロードすることはありません。[gtree をダウンロード](https://gtree.dobbylab.com/ja/)して、いま動かしているエージェントの横で使い心地を確かめてみてください。
